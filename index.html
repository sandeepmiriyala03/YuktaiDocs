YuktAI, documented and running live

YuktAI is an open-source toolkit for accessible, AI-assisted web apps: an accessibility widget, a data grid you can talk to, page Q&A, agents, icons and optional Rust engines. Use it in Next.js / React or in plain HTML with one script tag. Everything on this site runs in your browser, with no API keys and no server.

1. Install

Choose your stack once; every code block on this site follows your choice. Python (Django, Flask, FastAPI) has its own page.

Terminal

index.html (before </body>)
<script src="https://cdn.jsdelivr.net/npm/@yuktishaalaa/yuktai@5.3.9/vanilla/index.min.js"></script>

pip install yuktai

2. First use in two minutes

app/YuktaiClient.tsx
"use client"
// YuktAI's components use browser APIs, so they live in a client component.
import { YuktAIWrapper } from "@yuktishaalaa/yuktai"
import type { ReactNode } from "react"

export default function YuktaiClient({ children }: { children: ReactNode }) {
  return (
    <YuktAIWrapper position="left" launcher showAccessibility showRag engine="rust">
      {children}
    </YuktAIWrapper>
  )
}
app/layout.tsx
import type { ReactNode } from "react"
import YuktaiClient from "./YuktaiClient"

export default function RootLayout({ children }: { children: ReactNode }) {
  return (
    <html lang="en">
      <body>
        <YuktaiClient>{children}</YuktaiClient>
      </body>
    </html>
  )
}
index.html
<!doctype html>
<html lang="en">
<head><meta charset="utf-8"><title>My page</title></head>
<body>
  <main>
    <h1>Staff</h1>
    <div id="staff"></div>
  </main>

  <!-- 1. optional settings for the floating buttons -->
  <script>
    window.YUKTAI_CONFIG = { position: "left", showPageTools: true }
  </script>
  <!-- 2. YuktAI: adds window.yuktai and the ♿ / 🛠 buttons -->
  <script src="https://cdn.jsdelivr.net/npm/@yuktishaalaa/yuktai@5.3.9/vanilla/index.min.js"></script>
  <!-- 3. use it -->
  <script>
    yuktai.renderGrid("#staff", {
      data: [
        { id: 1, name: "Ravi Rao", city: "Hyderabad", salary: 120000 },
        { id: 2, name: "Asha Iyer", city: "Pune", salary: 85000 }
      ],
      columns: [
        { key: "name", label: "Name" },
        { key: "city", label: "City" },
        { key: "salary", label: "Salary", type: "number" }
      ],
      engine: "auto",
      showSearchTime: true
    })
  </script>
</body>
</html>

How YuktAI works

One codebase, two ways in

The npm package gives React components (YuktaiGrid, AgenticPanel, YuktAIWrapper, 163 icon components). The vanilla build is the same core code bundled into one script that adds window.yuktai. A question gets the same answer in both.

Private by design

Accessibility fixes, grid questions, page search, audits and the Rust engines all run in the visitor's browser. Nothing is sent to a server, and there is no telemetry.

Indic languages

Telugu grid UI and messages (locale: "te-IN"), Telugu-aware search tokens, Telugu custom rules for the assistant, and Telugu voice input where the browser supports it.

Rust when it helps

Set engine: "rust" (or "auto") for grid search/sort and page RAG. The WebAssembly is embedded in the script, so there is nothing extra to host, and TypeScript takes over if WebAssembly is not available.

Keeping up with new releases

  1. Try a new release on any page first: add ?v=5.3.10 (any version) to the address. It lasts for this browser tab; ?v=default goes back.
  2. For the whole site, change version in assets/js/config.js and the CACHE name in sw.js, then push. Netlify redeploys in under a minute.
  3. For your apps: npm install @yuktishaalaa/yuktai@latest, pip install -U yuktai, or change the version in the script URL.

Honest limits

  • Questions are understood with rules, not a language model, so unusual phrasing may need rewording. Telugu and Hindi data questions need custom rules.
  • Ask page is keyword retrieval (BM25), not embeddings: it finds passages that share words with the question. An English question will not match Telugu-only text.
  • QA, form and design checks are heuristics. Test with a keyboard and a screen reader before release.
  • Voice depends on the browser's speech recognition. Typed commands always work.
  • WebMCP needs document.modelContext; the real status is always reported.
